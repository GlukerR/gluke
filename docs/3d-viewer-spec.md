# ТЗ: 3D-вьюверы на сайте (Three.js) — для программиста

> Статус: **задача на реализацию, сайт ещё не тронут.** Этот документ — исходник
> для проверки и внедрения. Цель передачи: проверить, что всё согласуется с
> текущей архитектурой сайта, поправить спорные места и внедрить компоненты.
> Задача от владельца: «сделать 3D на Three.js со своими моделями».

---

## 1. Контекст и цель

Сайт — портфолио студии GLUKE (техническая 3D-визуализация: продукт, каталоги,
промо). Одна из продаваемых услуг — «3D-модели для веб-вьюверов» (GLB, WebGL,
интерактивный просмотр), см. `content/site/ru.yml` и `en.yml`. Живой 3D-вьювер
на собственном сайте — прямая демонстрация этой услуги.

Цель: в кейсах проектов появляются интерактивные 3D-модели — «покрутить» объект,
а для дрона — анимация сборки/разборки.

Кандидаты (модели уже есть у владельца):

| Кейс | Что показываем | Сценарий |
|---|---|---|
| **getic** | часть моделей роутеров MikroTik (лежат в папке Getic на диске D:) | орбитальная «крутилка», 1–3 модели |
| **kiparis** | 1 модель (диван/мебель) | «покрутить» |
| **fpv-frame** | дрон | **сборка/разборка** (анимация) |
| **wallcraft** | позже, когда клиент выложит модели в открытый доступ | обычный вьювер (движок клиента не важен — наружу выходит GLB) |

## 2. Текущая архитектура сайта (что уже есть)

- **Стек:** Nuxt 4.5, Vue 3.5, TypeScript, `@nuxt/content` 3.15 (SQLite,
  коннектор `better-sqlite3`), `@nuxt/ui`, i18n (`prefix_except_default`,
  EN без префикса, RU под `/ru`).
- **Контент кейсов:** `content/projects/ru/<slug>.md` и `content/projects/en/<slug>.md`.
  Схема — в `content.config.ts` (коллекция `projects`).
- **Медиа-схема** (`content.config.ts`, `mediaSchema`): сейчас `kind: 'image' | 'video'`,
  есть `poster`, `loop`, `autoplay`, `wide`. Изображения требуют `width`/`height`
  (реальные размеры файла).
- **Компоненты галереи:** `app/components/projects/ProjectMediaGallery.vue`
  (раскладка: первая и последняя записи на всю ширину, остальные парами)
  и `app/components/projects/ProjectMediaItem.vue` (ветки `kind: image` / `kind: video`).
  Страница кейса: `app/pages/projects/[slug].vue`.
- **Медиа-файлы:** `public/media/projects/<slug>/`. Папка `public/` отдаётся
  статикой — новые файлы попадают в прод автоматически.
- **Стандарты контента:** `CASE_TEMPLATE.md` (обложки, видео, чек-листы).
- **Конфигурация сайта:** URL приходит из переменной `NUXT_SITE_URL` (используется
  sitemap, robots, canonical, og:image). На прод — `NUXT_SITE_URL=https://gluke.ru`.

## 3. Выбор движка: Three.js (решение)

Сравнение под задачи сайта:

| Критерий | Three.js | @google/model-viewer | Babylon.js |
|---|---|---|---|
| «Покрутить» модель (getic, kiparis) | ✅ `OrbitControls` | ✅ из коробки | ✅ |
| **Сборка/разборка дрона** | ✅ полный контроль иерархии деталей | ❌ не поддерживает | ✅, но тяжелее |
| Встраивание в Vue/Nuxt | ✅ обычный npm-пакет | ⚠️ веб-компонент | ✅ |
| Вес, сложность, документация | лёгкий, MIT, лучшая экосистема | лёгкий | перегруз для портфолио |
| AR на телефоне | вручную (WebXR) | ✅ бесплатно | ✅ |

**Вывод:** основной движок — **Three.js** (`three`, MIT). `model-viewer` можно
держать как запасной вариант для простых «крутилок» без кастомных анимаций,
но не как основу. Babylon.js для 4–5 вьюверов избыточен.

**Формат моделей:** **GLB + Draco-сжатие** — общий язык для всех источников
(Blender-экспорт; у Wallcraft внутри может быть что угодно — наружу всё равно GLB).

## 4. Спецификация компонента `ProjectModelViewer.vue`

Новый компонент в `app/components/projects/`. Требования:

1. **Только клиент, без SSR:** обернуть в `<ClientOnly>`; WebGL на сервере не рендерится.
2. **Ленивая загрузка:** движок (`three` + загрузчики) подтягивается динамическим
   `import()` только при появлении вьювера в зоне видимости (IntersectionObserver).
3. **Постер + кнопка «Включить 3D»:** до запуска WebGL показывается постер-кадр
   (JPEG из рендера, стандарт ≤200 КБ) и кнопка запуска. Это сохраняет лёгкость
   страницы (в духе существующих бюджетов контента).
4. **Управление:** орбита (`OrbitControls`), зум, автоповорот (по умолчанию включён,
   выключается флагом в контенте).

### Лёгкая анимация (что поддерживает Three.js)

- `AnimationMixer` + ключи: position/rotation/scale, морф-таргеты, скиннинг —
  запечённые анимации из GLB.
- Морф-таргеты (shape keys): антенны складываются, кнопки нажимаются — без рига.
- Программно в render-loop: вращение антенны/вентилятора, **мигание LED через
  `emissiveIntensity`** (10 строк, без геометрии).
- Камера: интро-облёт по сплайну на старте, потом отдаётся управление пользователю.
- Взаимодействие: drag, клик по деталям (hotpoints).

Идея для getic-роутера (лёгкий набор): мигающие статус-LED + медленный автоповорот
+ опционально интро-облёт; если у модели внешние антенны — их раскладывание
морф-таргетом. Ничего из этого не требует новых зависимостей.
5. **Сборка/разборка дрона** — два допустимых пути реализации:
   - **Запечённая анимация:** в Blender детали разложены по ключам → GLB с
     `AnimationClip` → проигрывается `THREE.AnimationMixer`, кнопка
     «Сборка/Разборка» (плей/реверс).
   - **Программный взрыв-вид:** детали в GLB с чистой иерархией (объекты названы
     в Blender) → слайдер/кнопки двигают группы вдоль осей. Без рига, гибче.
   Решение по дрону — на этапе реализации, зависит от доступности исходника
   (см. «Открытые вопросы»).
6. **Fallback:** если WebGL недоступен или модель не загрузилась — остаётся
   постер + короткое сообщение. Никаких крашей страницы.
7. **Доступность:** `alt` из контента — в `aria-label` контейнера; кнопка запуска —
   с осмысленным текстом (переводится через i18n, как остальные строки сайта).
8. **Стиль:** компонент вписывается в галерею — та же пропорция, что у постер-кадра
   (16:9), скругления/фон по образцу существующих медиа-элементов.

### Изменение схемы (`content.config.ts`) — предложение

Добавить `'3d'` в `kind` и ветку полей модели:

```ts
kind: z.enum(['image', 'video', '3d']),
// для kind: '3d'
// src: /media/projects/<slug>/<file>.glb
// poster: /media/projects/<slug>/<poster>.jpg  (обязателен — постер-кадр)
// width/height — размеры постера (визуальная схема уже требует)
// autoRotate: boolean (опционально, по умолчанию true)
// explode: boolean (опционально — режим взрыв-вида по иерархии, для дрона)
// playAnimation: boolean (опционально — автопроигрывание запечённой анимации)
```

`alt` — обязателен (описание модели, доступность). Флаги `loop`/`autoplay`/`wide`
к 3D не применяются. Схема остаётся обратносовместимой: старые кейсы без `kind: '3d'`
рендерятся как раньше.

### Изменение `ProjectMediaItem.vue`

Добавить ветку `kind === '3d'` → рендер `ProjectModelViewer` (передать `src`,
`poster`, `alt`, флаги). Раскладка галереи (`ProjectMediaGallery.vue`) не меняется.

### Зависимости

- `three` (+ `@types/three`), загрузчики: `GLTFLoader`, `DRACOLoader`,
  `OrbitControls` (из `three/examples/jsm/...` или `three/addons/...`).
- Никаких новых модулей Nuxt не требуется.

## 5. Стандарт 3D-контента (для подготовки моделей)

Зафиксировать в `CASE_TEMPLATE.md` (и в ваулте, папка `41_B2B/Сайт/`):

- **Формат:** GLB. **Поддержка Draco ставится в компонент с самого начала**
  (декодер ~150–250 КБ, лениво, только при встрече Draco-файла, кэшируется) —
  пока моделей в Draco нет, декодер не грузится вовсе, вес страницы не меняется.
  Файлы декодера — **обязательно локально** (`public/draco/`, статика своего
  сервера), не с CDN и без каких-либо внешних выгрузок.

  > **Общий принцип (решение владельца): всё локально.** Никаких внешних CDN,
  > сторонних хостингов и выгрузок на другие сайты: декодер, GLB, текстуры,
  > постеры, шрифты — всё отдаётся с собственного сервера. (Шрифты Manrope идут
  > через `@nuxt/fonts` — проверить, что при сборке они self-hostятся локально
  > и в проде не дёргается Google.)

  Решение по конкретной модели — замером, правило:
  - **Квантование (`KHR_mesh_quantization`, «Quantize» в Blender) — всегда,
    бесплатно, без декодера.** Это 80% эффекта.
  - Лёгкая геометрия (роутер, мебель, < ~1–2 МБ квантизованных) → можно без
    сжатия меша вовсе.
  - Тяжёлые/hero-модели (дом 17 МБ и т.п.) → **Draco оправдан**: экономия мегабайт
    за разовые 200 КБ декодера. Сначала `Decimate` (150–300K треугольников для
    вьювера), потом Draco; текстуры — WebP + даунсайз до 2K (у домов часто
    доминируют именно текстуры).
  - meshopt (`EXT_meshopt_compression`) — альтернатива, если важен быстрый декод
    на слабых телефонах: декодер ~10–15 КБ, декод почти мгновенный, файл чуть больше.
  **Проверка перед публикацией модели:** `npx gltf-transform inspect` (расклад
    геометрия/текстуры), экспорт 3–4 вариантов (сырой/квантованный/+Draco/+meshopt)
    со сравнением весов, замер декода в браузере (Network + Performance, и на
    телефоне среднего класса). Решение — по цифрам.
  **Компонент должен абстрагировать загрузчик** — смена Draco↔Meshopt = одна строка
  (оба идут через `GLTFLoader`; Draco требует `setDecoderPath`, meshopt —
  `meshopt_decoder`).
- **Текстуры:** ≤2048×2048, **WebP** (экспортёр Blender умеет, `KHR_texture_webp`,
  Three.js читает; все текстуры сцены одного формата). KTX2 (GPU-сжатие) — НЕ нужно
  для этих моделей: добавляет KTX2Loader + WASM-транскодер, выигрыш на мелких
  сценах невидим. Запасной уровень на будущее, если сцены раздуются/просядут
  мобильные. Сжатие меша и текстуры — независимы: Draco не трогает текстуры.
- **Постер-кадр:** JPEG 16:9, ≤200 КБ (по образцу обложек), имя
  `<slug>-model-poster.jpg`.
- **Именование:** `<slug>-model-<номер>.glb` (например `getic-router-01.glb`).
- **Для взрыв-вида:** в Blender детали названы осмысленно (`panel_left`, `fan`…),
  иерархия чистая; трансформации применены.
- **Для запечённой анимации:** длительность 3–8 с, петля опциональна.
- Каждый GLB и постер — в `public/media/projects/<slug>/` (попадают в прод
  автоматически).

### Оптика, UV-наборы и повторяющиеся детали (дополнено 12.09.2026)

Правила для моделей, которые показываются конфигуратором с обвесом и окраской
(`ProjectCarConfigurator.vue`):

- **Оптика (фары и стопы) — отдельным материалом или нодой**, в имени которых
  есть `lamp`, `light` или `emissive`: `m_LampFront`, `m_LampRear`, `lamp_rear_a`,
  `headlight_left`, `white_emissive`. Колпак (`lamp`/`light`) делается
  **диффузорным стеклом с преломлением**: transmission 0,86 и толщина 0,6 дают
  настоящий сдвиг фона за стеклом (three рендерит непрозрачную сцену отдельным
  проходом и смещает её по ИОР), лёгкое поглощение в толще — зеленовато-голубое,
  как у поликарбоната. Альфа угловая: анфас — молочная плёнка (0,35), чтобы
  голые диоды не просвечивали, по касательной — зеркало (0,85) с холодным
  бликом кромки. Чистое стекло (анфас 0,06) тоже пробовалось: фара читалась
  окном в нишу с голыми квадрами внутри; тонировка же глушила свечение — в
  кадре на фаре оставался 1 % светлых пикселей вместо 23 %. Свечение даёт
  отдельный элемент за колпаком (`emissive`/`glow`/`drl` в имени): белое
  спереди, красное сзади. Светящиеся элементы должны лежать **внутри**
  колпака — иначе их не видно через него.

  Сам светящийся элемент — **не плоская наклейка**: остров оптики выгибается
  чашей (нормаль уводится от нормали площадки к её краю), поэтому отражение
  окружения ложится по отражателю, а свечение идёт от горячего ядра к тусклому
  краю с яркой полосой между ними. Ядро и чаша читаются только у **невыбеленной**
  яркости: элемент светит мимо тонмаппинга, и всё выше единицы — уже чистый
  белый (на 3,2 площадка была белой целиком, выгиб не давал ни одного пикселя
  разницы).
  Сторона берётся из имени
  (`front`/`rear`/`back`/`tail`/`headlight`, а у светящихся элементов — из цвета
  свечения: `white` — фары, `red` — стопы); если сторона не названа (одна общая
  метка вроде `m_Lamp` на обе оси) — делится по положению между бамперами.
  **Разделитель считается по мировым координатам бамперов и переносится
  в систему координат меша**, поэтому смещение ноды кузова (у машины — почти два
  метра по длине) разделению не мешает; в этом и была ошибка: мировая плоскость
  на локальной геометрии отсекала всю оптику в одну сторону, и общая метка
  оставалась тёплой линзой без деления на фары и стопы.
- **Фары не оставлять внутри примитива остекления.** Если они лежат в одном
  меше со стёклами, отличить их нечем, и весь стеклянный материал уходит в стёкла:
  окна выглядят правильно, но оптика — тёмной линзой без свечения.
- **Светящиеся элементы** (LED-полосы, внутренности фар, подсветка салона) —
  своим материалом внутри прозрачного колпака: во вьюверах свечение включается
  по материалам с `emissive`. Свечение задаётся цветом в имени (`white_emissive` —
  фары, `red_emissive` — стопы): в GLB `emissiveFactor` для этого не нужен.
  Яркость задаёт вьювер (`CAR_LAMP.glow`: 1,15 у фар и 1,3 у стопов), и эти
  материалы он рисует **мимо тонмаппинга**, иначе яркий красный выцветает
  в розовый, а белый уходит в серый и фонари не читаются горящими; поэтому
  яркость и держится около единицы — выше неё поверхность выбеливается целиком.
- **Отражателя в модели нет — его рисует шейдер, и ему нужны острова.**
  Остров — связный кусок геометрии без общих вершин с соседями: у машины
  колпак — это шесть отдельных линз, а элементы фар — сотня отдельных квадов
  (от 1 до 19 см), которые в Blender лучше сводить в осмысленные модули.
  Вьювер считает острова сам (`lampIslandAttributes`) и кладёт на вершины две
  вещи: место вершины внутри своего острова и его длинную ось. Развёртку для
  этого брать нельзя — у площадок она своя и часто отсутствует.
- **UV-наборы:** вьюверу нужен только `TEXCOORD_0` (маска зон в `baseColorTexture`).
  Тайловые карты (узор, карбон, шлифовка) считаются проекцией по мировым
  координатам, вторые наборы не читаются — `TEXCOORD_1`/`TEXCOORD_2` из экспорта
  убирать.
- **На колесе металл и резина — разные материалы.** Обод рисуется не зоной
  маски (у `M_Rim` это квадрант салона, то есть чёрный), а отдельным металлом:
  вьювер даёт светлый металл деталям внутри нод колёс, если в имени ноды или
  материала есть `rim`, `disc`, `metal`, `chrome`, `alloy`. Шина (`M-Tire`)
  в этот набор не попадает и остаётся чёрной резиной. Требование одно: **шина
  должна сохранить своё имя** — если `palette` или ручная правка отдаст ей
  `M_Rim`, в металл уйдёт всё колесо.
- **Повторяющиеся детали (колёса) — одна геометрия и несколько нод:** в Blender
  это связанные дубликаты (Alt+D), glTF отдаёт несколько нод с одним мешем, вес
  не растёт, в three геометрия тоже одна. Правую сторону лучше повернуть на 180°,
  а не зеркалить масштабом −1: отрицательный масштаб переворачивает нормали и
  винтинг. Годится и GPU-инстансинг (`EXT_mesh_gpu_instancing`), three читает его
  сам, но инстансы — это один объект: вариантами комплектации их не сделать,
  да и в кадре они неотличимы от одного меша. В новом экспорте rp-grand
  инстансинга нет — четыре отдельные ноды (`Wheel`, `Wheel.001`…`Wheel.003`)
  с одной геометрией.
- **Колёса должны попадать в экспорт вовсе.** В `export_car.py` (папка проекта
  заказчика) у колёс нет роли, поэтому прежние уровни пришли без них: машина
  в кейсе стояла на пустом месте. Нужна роль `wheel` в списке ролей экспортёра,
  и тогда колёса едут в GLB как обычные ноды.
- **Колёса/диски как вариант комплектации:** если колесо — нода с ролью и
  вариантом (`wheel` + `a/b/c`), конфигуратор покажет его отдельной группой без
  правок разметки — достаточно добавить роль в `CONFIGURABLE_ROLES`
  (`app/utils/carVariants.ts`).
- **Уровень без колёс больше не выглядит машиной на пустом месте.** Вьювер
  держит колёса подробного уровня в самой сцене (`lod-wheels`) и показывает их
  на любом уровне; если у уровня есть свои — показываются они. Это подстраховка,
  а не разрешение не экспортировать колёса: свои колёса на упрощённом уровне
  дешевле, они и нужны в парке ассетов.
- **Уровни детализации:** обвес, оптика и колёса экспортируются на каждом уровне,
  где они нужны. Если LOD1/LOD2 приходят одним мешем кузова, панель комплектации
  на них гаснет (решение: без пояснительной сноски), а машина остаётся без колёс —
  при переключении уровня это видно как рывок. **Уровни ставятся по LOD0:** вьювер
  один раз считает посадку по подробному уровню (единственному с колёсами) и этим
  же смещением ставит остальные, поэтому кузов при переключении не проваливается;
  свои нули у LOD1/LOD2 должны быть в той же точке, что у LOD0.
- **Паритет уровней проверяется, а не осматривается.** `pnpm check:lods`
  (`scripts/check-lod-parity.mjs`) ищет кейсы с `configurator.manifest`, читает
  JSON-чанки GLB (геометрия в draco не мешает: имена нод, материалы и объявленные
  `TEXCOORD_*` лежат рядом) и сверяет: ноды манифеста по факту в модели, наборы
  ролей, наличие колёс и UV-наборы — с подробным уровнем, а байты и трисы — с файлом.
  Упрощение уровня допустимо, но объявляется в манифесте полем `parity`
  (id уровня → причина); расхождение без записи (как и лишняя запись) — ошибка и
  ненулевой код возврата. Обязательное и без исключений — `TEXCOORD_0`: по нему
  маска зон, без него уровень теряет зоны (узор этого не боится: он проецируется
  по мировым координатам, поэтому LOD без `TEXCOORD_1` рендерится верно и объявлен
  как упрощение).
- **`gltf-transform optimize` нельзя запускать на конфигураторной машине как есть** —
  из его шагов четыре ломают ровно ту разметку, по которой работает конфигуратор:
  - `join` и `flatten` склеивают меши с одним материалом и сносят имена нод:
    обвес, двери и стёкла сливаются в кузов, панель вариантов пустеет.
  - `palette` сливает материалы с одинаковыми свойствами в один: по-разному
    названные `m_Interior`, `M-Tire`, `red_emissive`, `white_emissive`
    становятся `M_Rim` и `m_Lamp`. Зоны кузова это переживут — они берутся
    из UV-маски, а не из имени материала, — а оптика нет: свечение вьювер
    различает только по имени, и вся оптика превращается в прозрачный колпак
    без света.
  - `instance` заменяет повторяющиеся ноды одним узлом с `EXT_mesh_gpu_instancing`
    и имени этому узлу не даёт: манифест на колёса больше не ссылается, и перенос
    колёс на упрощённые уровни их не находит.

  Экономит при этом не `instance`, а `dedup` вместе с `draco`: `dedup` сводит
  одинаковые меши к одному (четыре колеса — одна геометрия, имена нод остаются),
  а сжатие делает основную работу (тело и обвес 477 КБ → 60 КБ, колесо
  236 КБ → 32 КБ). Рабочий набор шагов: `weld`, `dedup`, `prune`, `sparse`,
  `draco`, `texture-compress`. После любого прогона сверять расклад:
  `node scripts/inspect-glb.mjs <file.glb>` (ноды и меши) и
  `node scripts/glb-report.mjs <file.glb>` (расширения, что весит: карты или
  геометрия, материалы с их картами и габариты) — по этому отчёту решается,
  что сжимать и в каких единицах пришла модель.
- **Окружение (гараж) — отдельный GLB.** Машина садится на пол окружения, а не на
  нижнюю точку его габарита: низ зала задаёт плинтус, поэтому пол ищется
  пробами по габариту машины (`app/utils/garageFloor.ts`). Камера остаётся
  внутри стен, поэтому в файле нужен честный пол
  и замкнутые стены; если стена всё-таки открыта (пролёт, дверной проём), облёт
  камеры ограничивается дугой `configurator.garage.orbitFrom/orbitTo`, чтобы
  проём в кадр не попадал (замкнутому залу стопор не нужен: у rp-grand дуга не
  задана, и камера обходит машину полным кругом). По высоте камера держится в
  пределах
  `configurator.garage.tiltFrom/tiltTo` (градусы над горизонтом машины,
  дефолт 3…50 — выше видно крышу окружения); масштаб и поворот задаются контентом
  (`configurator.garage.scale/rotation`), а не подгоняются в модели — окружение
  рисуется в своих единицах. Текстуры окружения ужимаются
  `node scripts/squeeze-glb-textures.mjs in.glb out.glb --quality=80 --max-size=768`
  (гараж rp-grand: 1,60 МБ → 0,36 МБ; карты 1,43 МБ → 0,24 МБ, геометрия в draco
  всего 0,12 МБ — поэтому сжимать имеет смысл именно карты). Скрипт берёт любой
  вход: после чистки зала в Blender достаточно прогнать его заново — так же
  и с самим файлом в `public/media`, если чистить прямо в проекте.
- **Камера в зале ограничена реквизитом, а не только стенами.** Большой зал
  с чужими машинами, верстаками и антресолями нельзя снять с общей дистанции
  порядка `fit` модели: на 6–8 м от машины камера попадает внутрь реквизита
  (кадр затягивает чужим кузовом) или машина оказывается за ним. Поэтому у
  гаража свои `fit` и `zoomMax`: у rp-grand дистанция держится в районе 6,0 м,
  отъезд ограничен 6,9 м, а подъём — 38° (над машиной на ~4,5 м висит крыша зала,
  выше неё камера видит только перекрытие). Границы подбираются замером:
  в живом вьювере считаются прозрачные пиксели кадра и доля пикселей машины на
  облёте — дистанция и подъём берутся те, где ничего не теряется.
- **Автоповорота в конфигураторе нет.** Камера ходит только за мышью: в зале
  с реквизитом равномерное вращение само заводит кадр в чужую машину, а при
  осмотре комплектации оно мешает. Витринный автоповорот остаётся у обычного
  вьювера в шапке кейса (`model.autoRotate`), и в конфигураторе этот параметр
  игнорируется.
- **Игровой интерфейс конфигуратора.** Экран гаража не должен выглядеть как
  информационная карточка сайта. На мобильном кадр держит пропорцию 16:10,
  чтобы камера не отъезжала из-за высокой вертикальной панели; HUD использует
  компактную верхнюю плашку, нижний dock с иконками и панель настройки внутри
  кадра. Метрики рендера и служебная оговорка о колёсах из игрового режима
  убраны, сброс доступен только внутри панели.
- **Интерфейс конфигуратора живёт на кадре гаража, а не под ним.** Кадр —
  это экран игры: в нём только имя машины с номером уровня, полоса разделов
  (обвес, цвет, узор, покрытие, детализация), панель открытого раздела и
  кнопка музыки. Поясняющих подписей в кадре нет намеренно — ни «меняется
  на лету», ни «вращайте»: подпись поверх чужого интерьера читается как
  отладка. Всё, что относится к вьюверу, а не к машине (трисы, draw calls,
  оговорка «учёт без колёс», сброс), стоит под кадром. Состояние одно:
  `activeTab` — открытый раздел или режим осмотра; разделы объявлены одним
  списком `hudTabs`, поэтому вторая машина со спойлером получает свой раздел
  из манифеста, без правок разметки. Разметка HUD стоит рядом со сценой,
  а не внутри неё: у сцены `role="img"`, и для скринридера её содержимое не
  существует. Слой прозрачен для мыши (иначе камера перестала бы крутиться),
  а указатель возвращают себе только его части. На узком экране (`<900 px`)
  кадр получает игровую пропорцию, разделы превращаются в иконки, а панель
  открывается компактным листом внутри кадра.
- **Музыка зала идёт после картинки, а не вместе с ней.** Трек подключается
  только когда сцена собрана (модель, уровни и текстуры на месте), поэтому он не
  спорит с ними за канал: в сетевой панели mp3 идёт после GLB и карт. Играет
  с нулевой громкости и набирает её плавно — резкий старт в фоне слышен как
  «врубилось», — зациклен и выключается кнопкой в углу сцены (перечёркнутая
  нота). Браузер без действия пользователя звук не отдаёт: тогда трек встаёт
  на взвод, и его запускает первый же клик, тап или клавиша на странице.
  Поле — `configurator.audio` (один трек на кейс), код — `app/utils/garageAudio.ts`.
  Треки из библиотек приходят в 256 кбит/с; для фона хватает 96 (`node
  scripts/squeeze-audio.mjs in.mp3 out.mp3 --bitrate=96`: у rp-grand 4,27 МБ →
  1,60 МБ, разница на слух в фоне не читается).
- **Печати (узоры кузова) — бесшовные картинки-тайлы, одна карта на печать.**
  В деплой идут два размера: `<id>-color.webp` (768 px) для шейдера и
  `<id>-thumb.webp` (96 px) — превью в панели, которая показывает все печати сразу
  (без превью браузер тянул бы сотни килобайт ради квадратиков 38 px). Собирает
  `scripts/fetch-car-textures.mjs` (блок `LOCAL`): новая печать — строка в скрипте,
  строка в `CAR_PATTERNS` (`app/utils/carMaterials.ts`) и подписи в i18n.

## 7. Открытые вопросы (решить до/в ходе реализации)

1. **Какие именно модели Getic грузить** — выбрать 1–3 роутера из папки
   (нужен список файлов, которые есть у владельца).
2. **Дрон:** запечённая анимация или программный взрыв-вид? Зависит от того,
   есть ли Blender-исходник с чистой иерархией деталей.

   (в документации фигурируют и Babylon.js, и Filament — разночтение в ваулте)
   не важен: принимаем GLB.
