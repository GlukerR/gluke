# Журнал изменений сайта GLUKE

**База сравнения:** архив `gluke-master.zip` (оригинал от программиста).
**Дата сверки:** 12 августа 2026.
**Как сравнивали:** архив распакован во временную папку, все исходники и структура
сверены с рабочим деревом (diff по файлам, проверка ссылок на медиа и компоненты).

Итог: **логика сайта не менялась** — правки касаются текстов, цветов, медиа,
раскладки и двух осознанных рефакторингов (общий контактный блок и смена SQLite-коннектора).

## 38. Производительность загрузки медиа на мобильном (22.08.2026)

Аудит lazy-загрузки картинок и видео в кейсах. Найдена и исправлена проблема с видео.

### Что было не так

Галерея кейса монтировала **все** `<video>` сразу при загрузке страницы с `preload="auto"` + `autoplay`. Браузер начинал скачивать каждый autoplay-ролик целиком, даже если галерея лежала на 2–3 экрана ниже. На мобильном это означало 5–11 МБ трафика при открытии кейса ещё до скролла:

|---|---|---|
| getic | 4 (10.7 МБ) | 10.7 МБ → 4.9 МБ (только первое, в радиусе вьюпорта) |
| hardi | 2 (9.2 МБ) | 9.2 МБ → 0 МБ |
| m1-group | 1 (10.7 МБ) | 10.7 МБ → отложено до скролла |
| cascadia | 1 (5.3 МБ) | 5.3 МБ → отложено |
| velesgard | 2 (6.9 МБ) | 6.9 МБ → 0 МБ |
| softlogic | 1 (3.8 МБ) + 3D | отложено |

### Исправление (`app/components/projects/ProjectMediaItem.vue`)

Ленивая активация видео через `IntersectionObserver` с запасом 1500px (~1.5 экрана):
- пока галерея не подошла к вьюпорту — `preload="none"`, без `autoplay`, показывается постер (свой у видео или обложка кейса); файл не скачивается;

- без IntersectionObserver (старые браузеры) — фолбэк на немедленную загрузку.

Картинки в кейсах и карточках уже были ленивыми (NuxtPicture `loading="lazy"` + avif/webp), hero — намеренно eager+preload. Правок не требовали.

## 39. Lighthouse performance — кейс getic (мобильный) и оптимизация LCP (22.08.2026)

Прогон Lighthouse mobile (412×823, slow 4G, 4× CPU) по `/ru/projects/getic` (кейс с 4 видео, без 3D) на свежей прод-сборке. Найдены и исправлены 3 проблемы:

### 1. Видео-постеры-фолбэки качали сырую обложку (771 КБ)

До раздела 38 видео-петли без собственного постера показывали обложку кейса, и браузер тянул сырой PNG обложки (771 КБ) ради подскролльного плейсхолдера. Исправление (`ProjectMediaItem.vue`): постер до активации — только свой (`item.poster`), фолбэк на обложку убран; петли без постера показывают фирменную подложку (как в оригинальном дизайне). Экономия 771 КБ и меньше конкуренции за полосу.

### 2. LCP-картинка качалась с Low приоритетом (LCP 22.5s → 9.5s)

`<link rel="preload" imagesrcset>` у hero-картинки Chrome грузит с приоритетом **Low**, а `fetchpriority="high"` на самом img не апгрейдит уже запущенный прелоад. Картинка ждала весь JS/wasm (LCP 22s ≈ TTI 22s). Исправление (`ProjectDetailHero.vue`): `preload` убран — img с `fetchpriority="high"` в SSR-HTML почти сразу после шапки качается первым. LCP: **22.5s → 9.5s**, TTI: 22.2s → 9.5s.

### 3. 3D-чанк (three.js + draco wasm ~0.7 МБ) грузился на кейсах без модели

Вьювер был статическим импортом — его чанк и draco wasm качались на всех кейсах, включая 13 из 16 без 3D. Исправление: `defineAsyncComponent` для `ProjectModelViewer` в `ProjectDetailHero.vue` и `ProjectMediaItem.vue` — чанк грузится только когда модель реально рендерится. На getic: draco-запросов **3 → 0**. Проверено на softlogic: канвас рендерится, GLB + draco грузятся, консоль чистая.

## 40. Качество превью-картинок карточек главной (22.08.2026)

Жалоба: превью кипариса на главной «шакальное» по сравнению с картинкой внутри кейса.

### Причина

На десктопе карточки 1–2 (`emphasis: 'tall'`) растягиваются по высоте на высоту широкого соседа (`flex: 1; height: 100%` в `ProjectCard`), и кадр становится заметно выше исходного 16:9: у кипариса кадр 370×449 CSS px при обложке 2:1. `object-fit: cover` при этом апскейлил выбранного кандидата по вертикали.

Кандидат выбирался по ширине (`sizes: xl:480px`), т.е. ~480w, а его высота (240 px у 2:1 обложки) не покрывала кадр 449 px — картинка растягивалась в ~1.9 раза. Внутри кейса та же картинка в своём соотношении — поэтому разница в качестве.

### Исправление (`app/components/home/HomeProjects.vue`)

Для высоких карточек добавлен отдельный `TALL_SIZES = '100vw md:50vw lg:64vw xl:960px'` — ширина заявлена с запасом, чтобы браузер выбрал кандидата, чьей высоты хватает на высокий кадр без upscale.

### Проверка (headless Chrome, CDP, 1440px)

| Карточка | Кадр | Кандидат (DPR1) | До | После |
|---|---|---|---|---|
| getic (lead) | 804×452 | 960×540 | 0.84 | ✅ |
| **kiparis (tall)** | 370×449 | 960×480 | **~1.9× upscale** | **0.94** ✅ |
